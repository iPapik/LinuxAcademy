# Полноценные учебные ВМ: Hyper-V, VMware или KVM

Эта часть курса предназначена для тем, которые нельзя корректно воспроизвести в OCI-контейнере: **systemd с PID 1, SSH и реальная сеть, загрузка GRUB, файловые системы, разделы, LVM, nftables/ufw/firewalld, rescue**. В версии 1.0 платформа автоматически проверяет задания в контейнерах; описанные ниже VM-практикумы выполняются на **отдельных гипервизорах** и не управляются веб-порталом. Эта граница принципиальна: сайт не хранит доступ к корпоративному Hyper-V и не получает привилегии гипервизора.

## Предлагаемая архитектура

Создайте отдельный учебный виртуальный коммутатор/VLAN **без маршрута в рабочие сети**. Разверните три ВМ:

| Название VM | ОС | Ресурсы | Диски |
|---|---|---|---|
| academy-u24 | Ubuntu Server 24.04 LTS | 2 vCPU, 2 ГБ RAM | 25 ГБ OS + 5 ГБ пустой |
| academy-d13 | Debian 13 | 2 vCPU, 2 ГБ RAM | 25 ГБ OS + 5 ГБ пустой |
| academy-a9 | AlmaLinux 9 | 2 vCPU, 2 ГБ RAM | 25 ГБ OS + 5 ГБ пустой |

Настройте локального пользователя `student` с собственным сильным паролем, консоль гипервизора, отдельные виртуальные сетевые адаптеры. Сделайте **эталонный снапшот** после установки и обновления. Для занятий выдавайте копии/клоны, а не общий экземпляр двум сотрудникам одновременно.

## Hyper-V: основные шаги

На Windows Server создайте виртуальный коммутатор **Private** для полной изоляции либо **Internal** для связи с хостом-гипервизором (это другой уровень доступности, учитывайте риски!). Не подключайте учебный vSwitch к боевому NIC.

1. В Hyper-V Manager выберите **New → Virtual Machine**. Для UEFI используйте поколение 2. На некоторых Linux ISO понадобится переключить шаблон Secure Boot на **Microsoft UEFI Certificate Authority** либо на время выключить Secure Boot для лаборатории.
2. Назначьте 2 vCPU, RAM 2–4 ГБ, основной VHDX динамический 25 ГБ. Создайте отдельно **второй пустой VHDX 5 ГБ** только для disk/LVM-тренировок.
3. Подключите ISO выбранного дистрибутива, установите ОС, SSH-сервер, стандартные администраторские утилиты.
4. Присоедините только к закрытому учебному виртуальному коммутатору, задайте статические адреса своей учебной подсети по утверждённой схеме.
5. Проверьте UEFI-загрузку, пользовательский вход и консоль виртуальной машины. Создайте контрольную точку `clean-install`.

Для VMware и KVM используйте аналогичный подход с отдельным виртуальным коммутатором/виртуальной сетью, клонами/снапшотами и вторым тестовым диском.

## Начальная подготовка Ubuntu / Debian VM

```bash
sudo apt update
sudo apt install -y openssh-server curl vim nano git sudo iproute2 iputils-ping \
  dnsutils traceroute lvm2 parted e2fsprogs rsync acl
sudo systemctl enable --now ssh
sudo systemctl status ssh --no-pager
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS
ip -br addr
```

## Начальная подготовка AlmaLinux 9 VM

```bash
sudo dnf install -y openssh-server curl vim nano git sudo iproute \
  iputils bind-utils traceroute lvm2 parted e2fsprogs rsync acl
sudo systemctl enable --now sshd
sudo systemctl status sshd --no-pager
lsblk -o NAME,SIZE,FSTYPE,MOUNTPOINTS
ip -br addr
```

## Практические задания для VM (с критериями проверки)

### VM-01. Системный сервис
Создайте `/etc/systemd/system/academy-demo.service`, который запускает `/usr/bin/sleep infinity`; `Restart=on-failure`, `User=student`. Проверьте `sudo systemctl daemon-reload`, `enable --now`, затем `status`. **Зачёт:** `systemctl is-enabled academy-demo` показывает enabled, `systemctl is-active academy-demo` — active. После рестарта VM unit автоматически стартует.

### VM-02. Сломанный unit
На клоне отредактируйте `ExecStart` тестового unit на заведомо неверный путь. Запустите и определите причину: `systemctl status`, `journalctl -u academy-demo -n 50`. Восстановите рабочий путь. **Зачёт:** есть описание первопричины, служба вновь active.

### VM-03. Пользователи и sudoers
Создайте группу `labops`, пользователя `labsvc` и каталог `/srv/labops` с setgid. Дайте только группе доступ. При необходимости добавьте точечное правило через `visudo -f /etc/sudoers.d/labops`. **Зачёт:** права `/srv/labops` 2770, группа правильная, `visudo -cf /etc/sudoers.d/labops` не выдаёт ошибку.

### VM-04. Отдельный диск + GPT
На **втором пустом** виртуальном диске найдите идентификатор `lsblk`. Создайте GPT и раздел для данных. Не трогайте основной диск с `/`. **Зачёт:** `lsblk` показывает второй диск, тип и новый раздел; выполнен снапшот до начала работы.

### VM-05. ext4 + постоянное монтирование
Создайте ext4 на тестовом разделе второго диска и смонтируйте в `/data`. В `/etc/fstab` используйте `UUID=...`, выполните `findmnt --verify`. Перезагрузите VM. **Зачёт:** `/data` доступен после рестарта и соответствует нужному UUID. Перед этим сохраните запасной доступ через консоль.

### VM-06. LVM
На отдельном чистом диске/разделе создайте PV, VG `academyvg`, LV `academylv`. Создайте ФС и точку монтирования. **Зачёт:** `pvs`, `vgs`, `lvs`, `findmnt` показывают ожидаемые значения. Не используйте раздел с установленной ОС.

### VM-07. Диагностика памяти
Запишите вывод `free -h`, `vmstat`, `top`, проанализируйте `MemAvailable`, load average, процессы с максимальным RSS. **Зачёт:** отчёт различает free/available/cache и не делает неверный вывод из одного показателя.

### VM-08. Журнал загрузок
Перезапустите test-VM, выполните `journalctl --list-boots`, `journalctl -b -1`, `journalctl -p err -b`. **Зачёт:** найдены сообщения текущей и предыдущей загрузки (при необходимости включено постоянное хранение journal).

### VM-09. SSH по ключу
Создайте Ed25519-ключ **на собственном учебном клиенте**, установите *публичный* ключ в `authorized_keys` VM. Проверьте вход. **Зачёт:** ключ авторизует пользователя, `~/.ssh` имеет 700, `authorized_keys` — 600. Приватный ключ никогда не попадает на портал.

### VM-10. Сетевая диагностика
Настройте учебные IP-адреса в закрытой подсети на двух VM. Проверьте `ip -br a`, `ip r`, `getent hosts`, `ss -lnt`, `curl` локального сервиса. **Зачёт:** приложены данные L3, DNS и прикладного уровня, не только успешный ping.

### VM-11. Firewall
На отдельной VM с гарантированным доступом через консоль разрешите SSH от учебной подсети и заблокируйте ненужный тестовый порт средствами ufw/nftables/firewalld по дистрибутиву. **Зачёт:** тест с другой учебной VM показывает разрешённый и запрещённый порт. Не проводите тест на рабочем SSH-сервере.

### VM-12. DNS resolver
Изучите, кто управляет `/etc/resolv.conf`, настройки resolved/NetworkManager. В учебной зоне создайте локальный resolver либо записи hosts. **Зачёт:** `getent hosts labnode` возвращает верный адрес, а конфигурация переживает перезапуск сети.

### VM-13. Ansible control node
Создайте отдельную Debian 13 VM-контроллер, установите `ansible-core`, inventory из двух учебных VM и SSH-ключ. **Зачёт:** `ansible all -m ping`, далее playbook создаёт пользователя и пакет, при втором запуске задачи возвращают ok без changed.

### VM-14. Playbook + handler
Создайте роль Ansible для шаблона конфигурации учебного HTTP-сервиса. При изменении шаблона handler перезапускает только нужную службу. **Зачёт:** первый запуск changed, второй идемпотентен, при обновлении шаблона срабатывает один handler.

### VM-15. Восстановление после ошибки
Используя снапшот VM, намеренно задайте ошибочный путь `ExecStart` в учебном сервисе и неисправный fstab только для необязательного учебного диска. Проверьте логи/консоль, верните исправления. **Зачёт:** загрузка и сервис восстановлены, написана последовательность действий и план отката. НЕ повреждайте рабочий загрузчик ОС без отдельного rescue ISO.

## Дальнейшее расширение

Чтобы прямо внутри браузера управлять **полными ВМ**, понадобится отдельный VM-runner: гипервизор с API (libvirt/Hyper-V/VMware), учёт выделенных ресурсов, подготовленные cloud-images, ограниченный консольный доступ и изоляция каждой VM. Эти функции не входят в текущий продукт; выдавать контейнеры за полноценные VM было бы технически неверно.
